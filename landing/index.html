Why we made it

There are a lot of tools like this.

We built this for ourselves because the alternatives felt harder to use than they needed to be.

There are other ways to run teams of agents. We found them complex to set up and difficult to keep using.

So we made our own. It made building teams straightforward, and using them became surprisingly pleasant. We are sharing it because it might make your work easier too.

How it works

From idea to working team.

set up → run → adjust
01 / SET UP

Start with a team.

Ask the manager to make one, copy a team you already like, or pick a template and brief it in plain language.

02 / RUN

Give it a goal.

Tell the team what you want and let it work. The agents take their roles and keep the context between turns.

03 / ADJUST

Get the result.

When it is ready, take the result. If something needs changing, talk to the manager and adjust the team or the goal.

Teams we keep coming back to

Real jobs for small teams.

examples from the workbench
01 / BUILD → TEST

Team A + Team B.

One team develops the project. Another checks the result on a remote machine, reports what broke, and sends the work back.

02 / TRY TO BREAK IT

The impatient users.

Small models get explicit instructions to behave like users with very little patience. They click around, complain clearly, and expose the rough edges.

03 / SHIP

The release crew.

A builder, a reviewer, and a tester turn a rough feature brief into a checked change with a record of what happened.

04 / TEACH

The education loop.

A planner, a content builder, and a critic shape a learning experience, then keep tightening it from the evidence.

05 / MOVE

The migration team.

A planner maps the change, an implementer does the work, and a verifier checks what moved before anyone calls it done.

06 / YOURS

Start with a manager.

Describe the job in plain language. The manager proposes the roles, starts the team, and helps you change it when the first pass teaches you something.
